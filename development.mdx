# How I built v1

v1 is intentionally minimal: it takes a LinkedIn connections export and loads it into **MotherDuck** so I can run repeatable queries and generate job-search outputs.

I optimized for two things:
- **Ship an MVP quickly** (prove end-to-end execution).
- **Keep the structure extensible** (so modeling and transforms are easy to add later).

## V1 Does Not include

### Additional non-connections data available from a linkedin export
Because I wanted to ship a V1 quickly, I did **not** include most of the data available via linkedin export.

That was a deliberate decision to keep v1 small and get to working outputs fast, while leaving plenty of potential roadmap items.

## What I did that makes transformations easy later

I made a few choices that keep the door open for a real model layer in v2.

### 1) Kept “raw ingest” conceptually separate
The v1 table is treated as **raw**.

That makes it easy to introduce:
- `stg_*` (light cleanup) tables
- `dim_*` and `fct_*` tables
- `*_v` views that become the contract for queries

without breaking the mental model of the pipeline.

### 2) Wrote queries as named, repeatable assets
Queries live as a “query pack” rather than ad-hoc SQL.

That matters because when more complex transformations are needed, I can:
- redirect queries to new views/tables
- keep the query intent the same
- validate outputs didn’t regress

### 3) Designed exports around job-search questions
I anchored outputs to questions like:
- “Who should I talk to next?”
- “Which companies show up most in my network?”
- “Which connections match my target personas?”

### 4) Left clear extension points
I set up the repo/docs so it’s obvious where v2 additions go:
- add data sources
- add new tables/views
- add new queries
- add new exports

This reduces friction when the project grows beyond one table.

## How I built it (sequence)

### 1) Define the outputs first
I started by listing the CSV outputs I wanted for the job search.

Then I wrote the SQL needed to generate them from a single table.
Only after that did I worry about structure and documentation.

### 2) Make ingestion reliable
I focused on getting a clean, repeatable load into a DB so the analysis wasn’t “spreadsheet brittle.”

### 3) Encode the job-search questions as queries
I captured each question as a named query so the workflow is repeatable after each LinkedIn export refresh.

### 4) Add docs while building
I documented the workflow and the extension points while the decisions were fresh.
